# 附录：预压缩产物（.zg/.br）

构建时用 `compression-webpack-plugin`、`vite-plugin-compression` 等插件，对最终产物额外生成一份压缩好的副本，文件名如 `app.8f3a2c.js.gz`、`app.8f3a2c.js.br`。

## 一、它们怎么用

部署时把 `.gz` / `.br` 和原文件**一起上传，保持同目录、同路径**（只是多了扩展名）。服务端收到请求时优先找预压缩文件，找不到再回退：

```nginx
# Nginx 典型配置
gzip_static  on;        # 有 .gz 直接发，不做实时压缩
brotli_static on;       # 有 .br 直接发（需 ngx_brotli 模块）
gzip off;               # 既然静态都有了，可关实时压缩（或保留兜底）
```

- 客户端带 `Accept-Encoding: br, gzip` → 优先发 `.br`
- 只支持 gzip 的老客户端 → 发 `.gz`
- 都不支持 → 回退原始文件
- 文件不存在对应压缩副本 → 回退原始文件或动态压缩（取决于配置）

## 二、和服务端压缩策略的关系

两者是**同一目标的两种实现时机**，不是重复功能：

| | 动态压缩（`gzip on`） | 静态预压缩（`.gz`/`.br`） |
|---|---|---|
| 压缩时机 | 每次请求实时做 | 构建时一次性做好 |
| CPU 开销 | 每个请求都吃 CPU | 请求时零压缩成本 |
| 压缩等级 | 通常取中间档（权衡延迟） | 可以用最高档（brotli level 11） |
| 效果 | 一般 | 同等级下体积更小 5%~15% |
| 小文件 | 收益被 CPU 开销抵消 | 仍可直接命中 |

实践上三种组合：

1. **Nginx 直出**：`gzip_static on` + `brotli_static on` 为主，关掉动态压缩或仅留兜底。QPS 高、CPU 敏感场景的标准做法。
2. **CDN 场景**：很多 CDN 会自己对可压缩类型做动态压缩，此时源站的 `.gz`/`.br` 不是必须的。但如果 CDN 支持"回源取预压缩文件"（或你把压缩产物一并上传），预压缩仍然更优——压缩档位更高、边缘节点不用再花 CPU。
3. **全静态托管 / OSS + CDN**：直接上传全部产物（含 `.gz`/`.br`），由回源层或服务端逻辑识别 `Accept-Encoding` 选文件。

## 三、注意事项

- **只对文本类资源有效**：JS/CSS/HTML/JSON/SVG。图片（PNG/JPEG/WebP）本身已压缩，再压只会浪费体积和 CPU，插件里要配置 `filter` 排除。
- **Brotli 只在 HTTPS 下生效**（浏览器策略），所以 `.br` 实际覆盖的是 HTTPS 流量，但现阶段这基本就是全部流量。
- **千万别双重压缩**：如果服务端配了动态 gzip 又找不到静态文件，会先压缩 `.br` 文件本身再发出去——所以要保证压缩副本与原文件同步部署，清理旧产物。
- **正确设置缓存**：产物带 hash 的静态资源配 `Cache-Control: immutable` 长缓存，预压缩副本共享同一策略。
- **`index.html` 这类无 hash 文件**也可以预压缩，但要配合协商缓存（ETag/Last-Modified），Nginx 的 `gzip_static` 处理 etag 没问题。
