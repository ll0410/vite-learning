# 12.3 SSR、SSG 与预渲染怎么选

ch12 的进阶列表只写了 `vite-plugin-ssr` 和 `vite-ssg` 两个名字，没有说明它们分别解决什么问题。CSR、SSG、SSR 不是「越新越好」的升级关系，而是三种不同的渲染时机，成本和收益差别很大。

::: tip 结论先行
- **适用**：对 SEO、首屏 HTML 或社交分享有硬要求的项目。
- **推荐**：内容型站点优先 SSG（构建期生成 HTML）；需要实时个性化再考虑 SSR；纯后台工具继续 CSR。
- **代价**：SSG 增加构建时间和页面数量；SSR 需要 Node 服务、缓存和降级方案，复杂度最高。
- **不要**：为了「看起来更现代」给教学 SPA 或内部后台引入 SSR。
:::

## 问题与判断

先看三种模式的核心差异：

| 维度 | CSR（当前项目） | SSG / 预渲染 | SSR |
| --- | --- | --- | --- |
| HTML 生成时机 | 浏览器执行 JS 后 | 构建期 | 每次请求 |
| 首屏内容 | 依赖 JS 下载与执行 | HTML 已包含内容 | HTML 已包含内容 |
| SEO | 较弱，依赖爬虫执行 JS | 好 | 好 |
| 部署 | 纯静态文件 | 纯静态文件 | Node / Serverless 运行时 |
| 缓存 | HTML 可协商缓存 | HTML 可长缓存 | 需按用户/参数设计缓存 |
| 复杂度 | 低 | 中 | 高 |
| 适合 | 后台、工具、强交互应用 | 博客、文档、营销页 | 个性化首页、登录态内容 |

判断顺序：

1. 页面内容是否对 SEO 或分享卡片有硬要求？没有就继续 CSR。
2. 内容是否在构建时就确定？是则 SSG，否则考虑 SSR。
3. 是否有能力维护 Node 运行时、缓存和降级？没有就不要选 SSR。

当前仓库是教学 SPA，页面内容不依赖搜索引擎收录，也没有服务端渲染需求。**不建议直接引入 SSR / SSG**；这一篇用于建立选型判断，而不是改造现有项目。

## 做法

### 1. Vite 官方提供的 SSR 基础能力

Vite 本身支持 SSR 构建：

```bash
# 示例：构建服务端入口（需要项目先有 entry-server）
vite build --ssr src/entry-server.ts
```

典型结构是：

- `src/entry-client.ts`：浏览器端挂载应用。
- `src/entry-server.ts`：服务端导出 `render` 函数。
- 开发期用 Vite 的 `createServer` + `ssrLoadModule`。
- 生产期由 Node 服务调用服务端产物生成 HTML，再注入客户端入口。

Vite 提供的是构建和开发能力，不提供路由、数据预取、缓存和部署方案。真正的 SSR 还需要框架或自研运行时补齐这些部分。

### 2. 社区方案怎么选

| 方案 | 定位 | 说明 |
| --- | --- | --- |
| `vite-ssg` | 构建期预渲染 | 适合路由相对固定的内容站，产物是静态 HTML |
| `vike`（原 `vite-plugin-ssr`） | 全功能 SSR / SSG 框架 | 提供路由、数据、预渲染等能力，学习成本更高 |

两者都**需要在接入前验证与 Vite 8 / Rolldown 1.2.19 的兼容性**。版本升级后，插件对构建钩子和产物格式的假设可能变化，不能仅凭历史文章判断可用。

### 3. 一个务实的渐进路径

如果只是想让少数营销页可被收录，不必整体上 SSR：

1. 保持主应用 CSR。
2. 对营销页、文档页单独做静态生成或预渲染。
3. 用反向代理按路径分发：静态页走 SSG 产物，应用页走 SPA。
4. 确认收益后，再评估是否统一到 SSR 框架。

这样可以把风险限制在少数页面，而不是一次性重构整个应用。

## 在本仓库验证

本篇不落地代码，用下面的清单做选型验证：

- [ ] 列出必须被搜索引擎收录的页面；如果为空，SSR / SSG 的优先级下降。
- [ ] 确认这些页面的数据是否在构建时可知；可知则优先 SSG。
- [ ] 评估部署环境是否支持 Node 运行时；不支持则排除 SSR。
- [ ] 评估缓存策略：SSR 页面能否按 URL 缓存，是否需要登录态。
- [ ] 选一个最小页面做 PoC，对比 CSR 与 SSG 的 HTML、LCP 和部署复杂度。
- [ ] 验证所选方案与当前 Vite / Rolldown 版本的兼容性。

如果 PoC 的收益不足以覆盖新增的构建、部署和调试成本，就保持 CSR。

## 常见坑

- **把 SSR 当性能银弹**：服务端渲染也要传输 JS 并水合，交互复杂时不一定更快。
- **SSG 页面数量爆炸**：每个路由都预渲染会显著增加构建时间，需要增量生成或按需生成。
- **hydration mismatch**：服务端与客户端首次渲染结果不一致，常见于随机数、时间、浏览器 API。
- **SSR 中直接访问 `window` / `document`**：服务端没有这些对象，需要在生命周期或环境判断中隔离。
- **缓存策略缺失**：SSR 每次请求都执行，没缓存时服务端压力远高于静态托管。
- **社区插件兼容性未验证**：旧版插件可能依赖已移除的构建行为。
- **为内部后台引入 SSR**：没有 SEO 收益，却增加了整套运行时成本。
