# Vite 插件教学文章写作

帮助不熟悉插件 API 的读者建立可复用的心智模型，而不是只罗列钩子、配置和术语。优先改善讲解顺序、示例完整度和信息分层，不把任务简化为润色句子或缩短篇幅。

## 遵守任务边界

- 先判断用户当前要求的是原因分析、优化方案、新建文章还是直接改写，只执行当前阶段。
- 用户要求先确认分析或方案时，不提前修改文档。
- 默认使用中文写作；用户指定其他语言时遵循用户要求。
- 只修改用户要求的文档及明确允许修改的内容，不为了文章示例顺手改动插件行为。
- 保留有价值的技术内容，通过重排和分层降低理解成本，不直接删除进阶知识。

## 先判断是否需要自研

新建或改写文章前，先回答“这个场景是否已经有 Vite 官方能力或成熟社区方案”。读者需要先完成选型，再决定是否跟着示例实现。

按顺序查证：

1. `docs/plugins/appendix-plugin-scenarios.md` 的「先查现成方案（总览）」。
2. `docs/plugins/appendix-plugins.md` 的插件清单与“按需”一栏。
3. Vite 官方文档中对应的配置项或钩子。
4. 候选社区插件的 README 与 `peerDependencies.vite`。

结论只能是以下四种之一：

- **官方已覆盖**：优先引用官方配置或钩子，不把自研示例写成唯一做法。
- **成熟社区方案**：给出插件名和仓库链接，必要时说明适用范围。
- **部分覆盖**：写清官方或社区覆盖了哪部分，本例补的是哪部分。
- **无通用方案**：说明为什么没有通用等价物，而不是只写“没有”。

未核实 Vite 8 兼容性的方案，必须标注“接入前需验证/实测”，不能凭插件名称推断可用。涉及版本前提时写明边界，例如本项目仍是 `vue-router@4.6`，不能直接使用 Vue Router 5 的 `vue-router/vite`。

新增或调整场景时，同步索引与附录总览；速览块本身不替代索引。

## 编写现成方案速览

每篇新建或改写的文章，都要在标题和 1–2 段导语之后、第一个 `##` 之前插入速览块。读者不滚动就能看到结论。

固定四行，顺序不可调整：

```md
::: tip 现成方案速览
- **官方 / 成熟方案**：方案名称、链接，必要时一句话说明适用范围。
- **覆盖程度**：**官方已覆盖** / **成熟社区方案** / **部分覆盖** / **无通用方案**（可加一句限定）。
- **本例定位**：教学用最小实现，重点是理解 `…`；生产项目优先使用上面的方案，不要照搬本例。
- **值得自研的时机**：写出具体的团队约束或业务条件；没有则写“通常不需要自研”。
:::
```

- 四行都必须存在；“本例定位”必须出现“教学用最小实现”和“不要照搬本例”。
- 链接只放已核实的官方文档或仓库；没有链接时写清来源，不编造 URL。
- 覆盖程度只能使用上面四种标签，不新增近义词。
- 速览块只给结论，不展开实现；实现细节仍放在正文。
- 文末 `## 进阶参考` 下必须回指速览块：

```md
> 现成方案与自研边界见文首「现成方案速览」，下面只讨论本例没有覆盖的部分。
```

## 写作前核对事实

动笔前阅读与文章直接相关的材料：

1. 该场景的官方能力、成熟社区插件与 Vite 8 兼容性。
2. 插件源码及导出的工厂函数、选项接口和主要辅助函数。
3. 插件注册位置及 Vite 配置接入方式。
4. 生成模块、转换结果或构建产物的实际消费者。
5. 相关类型声明、fixture、示例页面和验证脚本。
6. 文档中引用的命令、路由、文件路径和预期输出。

先整理一张事实卡，再设计文章结构：

- 要解决的具体问题。
- 现成方案与覆盖程度。
- 本例没有覆盖、值得自研的部分。
- 输入是什么。
- 插件实际生成、转换或拦截了什么。
- 谁消费输出或接收副作用。
- 读者能观察到的最终结果。
- 哪些钩子是核心，哪些只是接入细节。
- 开发时更新、构建时输出和错误分支是否与主题相关。

不要凭函数名猜测行为。无法从源码确认的内容应标明未知或继续查证，不编造生成结果。

## 设计递进主线

### 一篇文章先建立一条共同主线

使用“输入 → 插件处理 → 输出或副作用 → 应用消费 → 可观察结果”贯穿全文。

代码生成类插件应明确呈现“输入 → 生成 → 消费 → 结果”。其他插件使用对应的完整闭环：

| 插件类型 | 必须展示的闭环 |
| --- | --- |
| 虚拟模块或代码生成 | 源数据或目录 → 生成模块源码 → import 消费者 → 应用效果 |
| 代码转换 | 原始源码 → 转换后源码 → 转换条件与边界 → 行为变化 |
| 开发服务器中间件 | 请求 → 中间件分支 → 响应或 next → 客户端结果 |
| HTML 转换 | 原始 HTML → 注入或改写后的 HTML → 浏览器效果 |
| 构建产物处理 | 输入 chunk 或配置 → 产物修改或 emit → 最终文件与用途 |

### 一个主示例优先

- 选择一个最小但完整的真实示例贯穿核心章节，不让读者同时追踪多组文件名和变量。
- 同一插件包含两个功能时，先讲共同模型，再按复杂度依次讲两个闭环，不并行交叉叙述。
- 能从简单示例开始时，先简单后复杂。例如先静态组件注册表，再动态页面路由。
- 先回答“做什么、为什么需要”，再回答“用哪个钩子、如何实现”。
- 不按源码执行顺序机械堆砌 API；钩子应在读者已经理解其要解决的问题后出现。

### 明确阅读层级

- 选型结论：文首速览块给出的现成方案、覆盖程度和自研时机。
- 核心理解：问题、完整示例、生成或转换结果、消费方式。
- 实现细节：钩子、关键分支、更新机制、源码对应。
- 进阶参考：生产边界、性能取舍、SSR、复杂异常、常见坑。

进阶内容统一收口到 `## 进阶参考`，并在标题下回指文首速览块；项目使用 VitePress 时，可用 `::: details` 折叠较长的生产注意事项和常见坑。第一遍阅读不应依赖进阶概念。

## 展示完整示例

每个核心示例至少包含以下四步，可使用显式小标题：

1. **输入**：真实文件、请求、源码、HTML 或构建对象。
2. **生成或转换**：展示处理后的实际代码、响应、HTML 或产物，而不只展示处理算法。
3. **消费**：展示哪个模块、中间件、路由器或部署流程使用结果。
4. **结果**：说明页面、命令、网络请求或构建目录中能看到什么。

遵守以下示例规则：

- 代码生成文章必须同时展示“如何生成”和“生成后长什么样”，后者不能被省略。
- 优先摘录与当前主线一致的真实源码，省略无关类型或分支时注明“省略无关代码”。
- 使用简化函数、虚构辅助函数或伪代码时，明确标注“简化示意”或“伪代码”，不要让读者误以为能在源码中搜索到。
- 文件路径、路由名称、生成名称、import 路径和产物名称必须与项目事实一致。
- 不为追求“最小”而把多个新概念压缩进同一段代码。最小示例应易于理解，而不只是行数少。
- 静态导入、动态导入、HMR、source map、chunk 等概念只有与当前示例直接相关时才引入。

## 推荐文章结构

可按插件类型合并章节，但不得省略完整闭环、源码对应和可验证结果。

1. **场景与现成方案速览**：说明重复工作或具体问题，先给出四行选型结论，再用通俗语言概括插件做法。
2. **最终结果与共同数据流**：先让读者知道文章最终会得到什么。
3. **第一个完整示例**：输入、生成或转换、消费、结果。
4. **核心机制**：解释该示例涉及的钩子与数据流，避免无关 API。
5. **第二个递进示例**：仅在插件确有多个核心能力时使用，复用第一例建立的模型。
6. **对照真实源码阅读**：用表格关联文章步骤、真实函数或钩子、职责。
7. **关键更新或边界行为**：用对比表解释不同输入为何走不同分支。
8. **最小接入信息**：注册位置、必要类型声明和消费者，不展开整个项目骨架。
9. **验证步骤**：按页面结果、生成结果、更新结果、构建结果逐层检查。
10. **进阶参考**：生产级缺口、常见坑和可选深入主题。

## 控制表达与认知负荷

- 每段只回答一个问题，不在同一段混合应用接入、HMR、构建优化和生产边界。
- 一个句子尽量只承载一个主要判断；长句按“原因—动作—结果”拆分。
- 术语首次出现时采用“通俗定义 + 正式名称 + 在当前示例中的作用”，随后再讲细节。
- 区分“第一遍必须理解”和“暂时知道即可”，不要让所有术语看起来都是前置知识。
- 避免连续罗列多个钩子、模块名和内部变量而没有具体示例承接。
- 少用“本项”“共享骨架”“前文第几项”等依赖外部上下文的指代，直接写功能或文件名称。
- 保持术语一致，不在“目录结构变化”“文件结构变化”“清单刷新”等近义说法之间无意切换。
- 对比不同机制时优先使用简短表格，再解释读者最需要记住的原因。
- 不用抽象名词替代具体动作。优先写“插件扫描目录并返回源码”，少写“实现模块资源的动态生成与消费”。

## 编写源码对照

为核心步骤提供真实源码映射，至少包含：

| 文章步骤 | 真实函数或钩子 | 读者应关注的职责 |
| --- | --- | --- |
| 获取输入 | 实际扫描、配置或请求处理代码 | 输入从哪里来 |
| 生成或转换 | 实际 load、transform、中间件或构建钩子 | 输出如何产生 |
| 消费结果 | 实际 import、路由、HTML 或部署代码 | 输出如何生效 |

不要在文档中硬编码容易变化的源码行号，使用文件名、函数名和钩子名定位。

## 编写可验证步骤

每个验证步骤都写清“执行什么”和“预期看到什么”。

- 页面验证：给出入口和可观察结果。
- 生成结果验证：给出 Inspect、curl、转换输出或文件位置，并描述关键内容。
- 更新验证：说明修改、新增或删除后，什么应变、什么不应变。
- 构建验证：说明应出现哪些产物或 chunk，以及如何确认能够加载。
- 临时验证文件需要删除时明确提醒，不把临时状态当作最终示例。

不要只罗列命令。无法从当前项目确认的端口、路径和输出不要照搬到新文章。

## 完成前质量检查

### 选型与速览

- 速览块位于首个 `##` 之前，且只有 1 个。
- 四行齐全，覆盖程度使用允许的四种标签之一。
- 方案名称、链接、兼容性表述可核实；未验证项已标注。
- “本例定位”明确说明教学用途，未暗示必须自研。
- 文末恰好 1 个 `## 进阶参考`，并包含回指句。
- 正文没有与速览结论冲突的推荐。

### 理解路径

- 读者不阅读其他章节，也能理解核心完整示例。
- 开头能看懂插件解决什么问题，以及最终得到什么。
- 生成或转换结果有实际展示，不需要读者在脑中推演全部输出。
- 多能力插件没有两条主线交叉推进。
- 核心内容与进阶内容有明确层级。

### 技术一致性

- 文档函数名、文件名、路径、路由和产物与真实源码一致。
- 简化代码和伪代码有明确标识。
- 每个生成或转换结果都有消费者或可观察副作用。
- 命令、curl 地址和验证预期与项目配置一致。
- 原有重要技术信息被保留或有意去重，没有因缩短文章而丢失关键边界。

### 阅读体验

- 没有连续多段只讲 API 而没有示例。
- 没有单段同时承担多个抽象层级的信息。
- 术语首次出现有通俗解释。
- 读者能复述输入、输出、消费方、最终结果，以及核心钩子的存在原因。

## 验证并报告

完成新建或改写后：

1. 对目标文档运行 `git diff --check`。
2. 项目提供文档构建命令时运行构建；本仓库使用 `pnpm docs:build`。
3. 检查 Git 状态，确认没有意外修改插件源码或生成额外交付文件。
4. 用 Grep 确认目标文章 `::: tip 现成方案速览` 与 `## 进阶参考` 各出现 1 次；速览块行号应小于首个 `##` 行号，`## 进阶参考` 下应有回指句。
5. 简要报告文章结构调整、技术核对结果和构建结果，不宣称未执行的手工验证已经通过。
